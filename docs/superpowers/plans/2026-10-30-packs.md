# Rulesets and settings as packs Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A ruleset or a setting is a pack an install has, not code built into Delve. Delve ships core and OSRIC; AD&D 2e, Greyhawk and the Forgotten Realms become packs installed privately, and Delve starts and plays with none of them.

**Architecture:** A pack is a folder in `<data dir>/packs/<id>/` with a `pack.toml`, its Python code under `src/`, and its data. Core's `delve.packs` finds the installed packs at start, puts each one's `src/` on `sys.path`, and asks its entry object for a `Ruleset` or a `Setting`. The two catalogs are made from what it finds. In transit a pack is one `.delvepack` file: a zip with a checksum manifest, built and installed by `delve pack`. The single `reference.db` goes away: each pack builds its own `pack.db` from its own snapshots when it is installed.

**Tech Stack:** Python 3.13 (`tomllib`, `zipfile`, `sqlite3`, `importlib`), import-linter, pytest; React/TypeScript for the no-setting choice.

**Spec:** Tasker DEL-307: its description, the design comment (2026-10-29, "data packs, with the engine in core") and the owner's decisions (2026-10-30, comment 414). DEL-302's separation is already merged, so the game asks the campaign's ruleset and never `delve.rules.adnd2e`.

## Global Constraints

- Packs live in `<data dir>/packs/<id>/`, where the data dir is `DELVE_DATA_DIR`, else `~/.local/share/delve` (`config.py`).
- The transit format is a single `.delvepack` file (a zip), named `<id>-<version>.delvepack`.
- AD&D 2e, Greyhawk and the Realms go to a new **private** gitea repo, `raf/delve-packs` (https://192.168.86.29), with one folder per pack. The Delve repo keeps core and OSRIC.
- With no setting pack installed, a campaign has no setting. Greyhawk stays the default only where it is installed.
- Each task can be merged on its own, and a live 2e or Greyhawk campaign keeps playing after every task.
- Only the owner installs packs, from the CLI. A pack is code, so the web gets no pack upload in this plan.
- Migrations: plain `ALTER TABLE` on referenced tables, never a batch rebuild of `campaigns`. Take the next free number from master.
- Prose follows the repo's style: plain words, comments as dense as the surrounding code. Commits cite DEL-307.
- Not in this plan: rewriting old git history, pack help pages (no pack has any today), and installing packs from the web.

## Review Focus

1. **A campaign whose pack is missing.** A live campaign whose ruleset or setting is not installed must say so ("This campaign's ruleset, adnd2e, isn't installed") and refuse to play. It must not play on the fake ruleset, which is what `make_ruleset` falls back to today. → Task 4, `test_a_campaign_whose_ruleset_is_missing_refuses_to_play`.
2. **A broken pack.** A bad `pack.toml`, an import error, a wrong `delve_api` or two packs claiming one id must not stop Delve starting. The pack is left out, the log names it, and `delve pack list` shows why. → Task 1, `test_a_broken_pack_is_skipped_and_named`.
3. **A hostile or damaged `.delvepack`.** An entry with `..` or an absolute path, a symlink, a checksum mismatch, or an interrupted install must leave the installed pack as it was. → Task 2, `test_install_refuses_path_escape`, `test_install_refuses_bad_checksum` and `test_failed_install_keeps_the_old_version`.
4. **Upgrading a pack under a running Delve.** Installing a newer version replaces the folder in one rename, and `pack.db` is rebuilt before that rename, never after it. → Task 2, `test_reinstall_replaces_atomically`.
5. **Delve with OSRIC only.** No `reference.db` and no 2e or setting pack: `delve serve` starts, a new campaign is OSRIC with no setting, and a beat plays. → Task 10, the guard test and the e2e run.

## File structure

**Core (this repo):**
- `src/delve/packs/__init__.py`: what the package offers.
- `src/delve/packs/manifest.py`: `PackManifest`, which reads `pack.toml`.
- `src/delve/packs/api.py`: what a pack's entry object provides (`RulesetPack`, `SettingPack`), and `PACK_API = 1`.
- `src/delve/packs/loader.py`: finds and loads the installed packs.
- `src/delve/packs/transit.py`: builds, checks and installs `.delvepack` files, and removes packs.
- `src/delve/packs/store.py`: loads a pack's gzipped SQL and JSON snapshots into its `pack.db`, after checking `SHA256SUMS`. This is the generic half of today's `storage/reference/build.py`.
- `src/delve/__main__.py`: the `delve pack build|install|list|remove|rebuild` commands.
- `src/delve/rules/catalog.py` and `src/delve/setting/catalog.py`: entries made from loaded packs.
- `packs/osric/`: OSRIC as a pack, in this repo (Task 7).
- `tests/packs/`: the tests, and `tests/fixtures/packs/`, a tiny test ruleset pack and test setting pack.

**Private repo `delve-packs`:** `adnd2e/`, `greyhawk/` and `forgotten-realms/`. Each holds a `pack.toml`, `src/<package>/`, `data/`, `house-rules/` where it has any, and `tests/`. A `Makefile` runs each pack's tests with Delve's venv: `DELVE=~/claude/refactoring`, so `uv run --project $(DELVE) pytest <pack>/tests`.

**A pack's folder:**
```
<id>/
  pack.toml
  src/<package>/...      # the Python package; its name is in pack.toml
  data/                  # shipped data: JSON, *.sql.gz with SHA256SUMS
  house-rules/           # optional seeds, tagged with this pack's id
  tests/                 # source only; left out of a .delvepack
  pack.db                # made at install time, never shipped
```

**`pack.toml`:**
```toml
id = "adnd2e"                       # [a-z0-9-]+, the campaign's ruleset/setting id
kind = "ruleset"                    # "ruleset" | "setting"
title = "AD&D 2nd edition"
version = "1.0.0"
delve_api = 1
package = "delve_adnd2e"            # the top-level package under src/
entry = "delve_adnd2e.pack:PACK"
fact_categories = ["greyhawk", "history"]   # settings only: the lore fact categories it owns
```

### Task 2: The `.delvepack` transit format and `delve pack`

**Files:**
- Create: `src/delve/packs/transit.py`
- Modify: `src/delve/__main__.py` (the `pack` subcommands)
- Test: `tests/packs/test_transit.py`, `tests/test_cli.py` (the pack commands)

**Interfaces:**
- Consumes: `PackManifest.read`, `load_packs`, and `api.*Pack.build`.
- Produces:
  - `build_pack(folder: Path, out_dir: Path) -> Path`, which writes `<id>-<version>.delvepack`.
  - `install_pack(source: Path | str, packs_dir: Path) -> PackManifest`. The source is a `.delvepack`, a folder, or a git URL, optionally ending in `#<folder>` for a pack inside a repo of several. For a URL it runs `git clone --depth 1` into a temp dir, then installs that folder (or the named subfolder).
  - `remove_pack(pack_id: str, packs_dir: Path) -> None`.
  - `PackError(Exception)`.

The format is a zip, deflated.
- Its first entry is `pack.toml`.
- `MANIFEST` lists `<sha256>  <path>` for every other file.
- It holds every file of the folder except `tests/`, `pack.db`, `__pycache__/`, `*.pyc` and dot-files.
- Paths are POSIX and relative.

Installing goes like this:
1. Extract to `packs_dir/.incoming-<id>-<random>`.
2. Check every entry against `MANIFEST`, and refuse an absolute path, `..`, a symlink, or a file not in `MANIFEST`.
3. Read the manifest and import the entry in a subprocess (`python -c`), so a broken pack never enters the running interpreter.
4. Run `build(root, root/"pack.db")` there if the entry has one.
5. `os.replace` the old folder to `.old-<id>`, then the new one into place, then delete `.old-<id>`.

On any failure the incoming folder is deleted and the old pack stays.
