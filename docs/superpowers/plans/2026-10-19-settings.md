# Delve: Settings, implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The setting (Greyhawk today, more later) becomes a first-class area:
- organisers open **Settings** in the sidebar to search and read the wiki, add and override pages, add facts, own
  world maps, read the calendar, and accept the DM's proposals;
- player seats read the campaign's setting in a **Setting** tab of the play screen, never its DM-only content;
- the install's options page becomes **Preferences**.

**Architecture:**
- **One catalog** (`delve.setting.catalog`) names every setting once. The web registry and the DM's
  `CampaignContext` are both built from it.
- **The reference stays read-only.** The install's additions (new pages, overrides, facts), the DM's proposals and the
  setting's own world maps live in four new tables of Delve's database (migration `0016_setting_content`).
- **One setting layer** (`delve.play.setting_layer.SettingLayer`) puts them over the shipped setting. It implements the
  `Setting` protocol, so the DM's tools keep working through it, and it filters DM-only content for any reader that
  isn't the DM. Every reader goes through it: the DM's lookups and search, Ask the DM, "Did you know", the Settings
  area and the play screen's Setting tab.
- **Proposals** are records of their own (`proposals`). They apply at once to their own campaign's layer. They reach
  every campaign only once an organiser accepts them and they become ordinary additions.
- **Setting-owned world maps** are a third owner kind, `setting`, beside `module` and `campaign`, in every world-map
  route, the picture import, the review and the editor. The old pointers (`setting_world_maps`) are copied into
  setting-owned maps once, at start.

**Tech Stack:** Python 3.12, FastAPI, SQLAlchemy Core and alembic over SQLite, React 18 + TypeScript + React Query,
vitest, Playwright. No new dependency (`httpx`, already direct, serves the CLI command).

**Spec:** `docs/superpowers/specs/2026-10-19-settings-design.md`, all of it. The owner's decisions 1–8 and the
"Calls made for the owner" are fixed requirements. This plan settles "What's left to the builder" (see "Decisions taken
in this plan"). File references were checked on master b8009a6.

## Review Focus

1. **DM-only text in a search snippet or a fact list.**
   - A page an organiser added with a `::: dm` section holding `SECRET-XYZZY`, and a word that matches only inside that
     section.
   - A seat's search for that word finds nothing.
   - A search for another word of the page gives a snippet without the secret.
   - A DM-only fact or proposal is never in `…/setting/facts`, `…/lore/random` or Ask's prompt.

   (Task 4 layer tests; Task 8's and Task 6's fourth-wall plants.)
2. **Titles that aren't plain.**
   - `"Hardby"` asked as `"  hardby "`, and a redirect of two hops (`"Mordy"` → `"Mordenkainen the Mage"` →
     `"Mordenkainen"`, in the tiny reference).
   - A title with a slash, an apostrophe and a question mark (`"Ready'reat / Patchwall?"`) round-trips through PUT, GET
     and DELETE.
   - An override made through a redirect is stored under the target's title, and reverting it brings back the shipped
     page.

   (Task 2, 4 and 8 tests.)
3. **A proposal whose world moved on.**
   - An edit proposal accepted after an organiser overrode the same page appends to the override, not to the shipped
     text.
   - Accepting or rejecting twice is 409, and so is accepting a new-page proposal whose title an organiser has taken
     meanwhile.
   - A deleted campaign takes its pending proposals with it.
   - A second campaign sees an accepted proposal, and never a pending or rejected one.

   (Task 8 and Task 15 tests.)
4. **The setting's maps in odd states.**
   - The setting's only own map is in review: a new campaign still copies the built-in map.
   - Copying a module map under a name the setting has: 409.
   - A pointer whose module map was deleted, or is in review: dropped at start, nothing copied, the start goes on.
   - A hidden feature never reaches a seat's view of a setting map, by name or label.

   (Task 9 tests.)
5. **Search input that isn't words.**
   - `"`, `*`, `AND`, `-`, `%`, `_` and an empty query: the area's and the seat's search answer 200 with no or ordinary
     hits, never 500, and `%` doesn't match everything.
   - A page added with a non-Latin title and words (`Ærdy`, `Ūrnst`) is found by them.

   (Task 4 and Task 8 tests.)

### Task 2: The setting's content in Delve's database

**Files:**
- Create: `src/delve/domain/setting_content.py`, `src/delve/storage/sqlite/setting_repos.py`,
  `src/delve/storage/migrations/versions/0016_setting_content.py`
- Modify: `src/delve/storage/interfaces.py` (four protocols and `Storage`), `src/delve/storage/sqlite/tables.py`,
  `src/delve/storage/sqlite/__init__.py`, `tests/storage/contract.py`, `tests/storage/test_migrations.py`

**Interfaces:**
- Produces:
  - **`setting_content.py`** (frozen dataclasses; the dicts with `field(default_factory=dict)`):
    - `ProposalKind = Literal["page", "edit", "fact"]`, `ProposalStatus = Literal["pending", "accepted", "rejected"]`,
      `EditMode = Literal["append", "replace"]`;
    - `title_key(title: str) -> str`: the title with its whitespace collapsed to single spaces, casefolded;
    - `SettingAddition(setting: str, title: str, kind: str = "", fields: dict[str, str] = {}, text: str = "", dm_only:
      bool = False, created_at: str = "", updated_at: str = "")`. One per setting and `title_key`. `text` is Markdown
      with `[[Title]]` / `[[Title|label]]` links and `::: dm` sections (Task 4). Whether it is a new page or an override
      is never stored: it is an override when the shipped setting has a page of that title.
    - `SettingFact(id: int, setting: str, text: str, category: str = "", dm_only: bool = False, created_at: str = "")`;
    - `Proposal(id: int, setting: str, campaign_id: str, kind: ProposalKind, title: str = "", text: str = "", mode:
      EditMode = "append", page_kind: str = "", category: str = "", dm_only: bool = False, status: ProposalStatus =
      "pending", created_at: str = "", decided_at: str | None = None)`.
  - **`interfaces.py`:**
    - `SettingPageRepository`:
      - `get(setting, title) -> SettingAddition | None`, matched by `title_key`;
      - `list(setting, *, kind: str | None = None, query: str = "") -> list[SettingAddition]`, by title. `query`
        matches the title or the text, casefolded, in Python, never by SQL `LIKE`, so `%` and `_` are plain
        characters.
      - `put(addition) -> SettingAddition`: an upsert by `title_key`. It keeps `created_at` and sets `updated_at`, and
        the title's spelling is the latest put's.
      - `delete(setting, title) -> None`.
    - `SettingFactRepository`:
      - `get(id)` and `list(setting, *, query: str = "") -> list[SettingFact]`, oldest first;
      - `add(fact)`, which answers it with its id;
      - `put(fact)`, `KeyError` for an unknown id;
      - `delete(id)`.
    - `ProposalRepository`:
      - `get(id)`;
      - `list(setting: str | None = None, *, campaign_id: str | None = None, status: ProposalStatus | None = None, kind:
        ProposalKind | None = None) -> list[Proposal]`, oldest first;
      - `add(p)`, `KeyError` for an unknown campaign;
      - `put(p)`, `delete(id)`.
    - `SettingMapRepository`:
      - `get(setting, name) -> WorldMapSource | None`;
      - `list(setting) -> list[WorldMapSource]`, in the order first put;
      - `put(setting, world_map) -> WorldMapSource`, `ValueError` when `world_map.geo` is None (a setting's map is
        always a Delve document);
      - `delete(setting, name)`.
    - `Storage` gains `setting_pages`, `setting_facts`, `proposals`, `setting_maps`. `setting_world_maps` stays, for
      Task 9's adoption.
  - **The tables** (`tables.py`, the migration the same):
    - `setting_pages(setting, title_key, title, kind, fields JSON, text, dm_only, created_at, updated_at)`, primary key
      `(setting, title_key)`;
    - `setting_facts(id INTEGER PK, setting, text, category, dm_only, created_at, updated_at)`;
    - `proposals(id INTEGER PK, setting, campaign_id → campaigns.id ON DELETE CASCADE, kind, title, text, mode,
      page_kind, category, dm_only, status, created_at, decided_at NULL)`, indexed on `(setting, status)` and
      `campaign_id`;
    - `setting_maps(setting, name, title, geo JSON NOT NULL, picture NULL, status, reading JSON NULL, created_at,
      updated_at)`, primary key `(setting, name)`.
  - **Migration `0016_setting_content`** (`down_revision = "0015_costs"`) creates the four tables, and its downgrade
    drops them. No other table changes.

## Decisions taken in this plan

Taken by the quest's rules ("proceed": design questions answered by recommendation). The owner's decisions 1–8 and the
spec's "Calls made for the owner" stand as written.

| # | Question (spec: "What's left to the builder") | Answer | Why |
|---|---|---|---|
| 1 | Table shapes | Four tables: `setting_pages` (new pages and overrides alike), `setting_facts`, `proposals`, `setting_maps`. An addition's being an override isn't stored: it is one when the shipped setting has that title. | One page table keeps one title rule; the shipped side decides "override" live, so a rebuilt reference can't leave a stale flag. |
| 2 | How a DM-only section is marked | A fenced block: a line `::: dm`, the text, a line `:::`. A whole page or fact has its own `dm_only` flag. | It reads plainly in a textarea, never clashes with Markdown or wiki markup, and is stripped by one function on the server. |
| 3 | Override matching | By title, whitespace collapsed and casefolded (`title_key`), after the shipped redirects: an override is stored under the shipped page's canonical title. | The reference already matches titles without case and follows redirects; the override then always shadows the page a reader reaches. |
| 4 | Search order | This campaign's proposals, then the install's additions, then the shipped FTS hits (without the titles an addition replaced), then facts. | The install's and the table's own words are what the reader most likely means; the shipped wiki is the large rest. |
| 5 | Lore facts per setting | No reference change: a catalog entry names its fact categories (Greyhawk: `greyhawk`, `history`), and a setting leaves out the categories other settings claim. Rules, monster, spell, magic, class and planes facts stay general. | The reference stays as built; a second setting needs one catalog line. |
| 6 | DM proposal tools | `propose_page(title, text, kind?, dm_only?, mode?)` (a new page, or an edit when the title exists; `append` by default) and `propose_fact(text, category?, dm_only?)`, both DM-only, beside `add_fact` in `dm/tools/lore.py`. | Named and shaped like `add_fact` and `setting_lookup`; append is the common case (an NPC's fate), and replace is there for the rest. |
| 7 | Merging proposals | One campaign's pending proposals of the same kind and title merge into one: an append joins, a new page or a replace replaces. Facts never merge. | The organiser reviews one item per page, and nothing the DM wrote is lost. |
| 8 | Pointers to copies | Not in the migration (which can't run Delve's map conversion): at start, `adopt_pointers` copies each pointed ready module map as a setting-owned GeoJSON map and deletes the pointer; what it can't copy is dropped. The table stays for now. | Idempotent, runs on every install at its next start, and keeps a schema-only migration like the others. |
| 9 | Setting map storage | Always a Delve GeoJSON document (`geo` required), never a `.map` with includes; the built-in `.map` stays the shipped setting's. | No include fragments to carry; the picture import and GeoJSON import already produce documents. |
| 10 | DM-only override | A DM-only override is the DM's version: seats keep seeing the shipped page. | The shipped wiki is public lore (spec); hiding it would hide what players may read anyway. |
| 11 | The owner's seat on the play screen | The Setting tab's routes filter for every caller, the owner's seat too. | "read-only and without DM-only content" for the tab; organisers have the area for the rest. |
| 12 | Wiki markup | Converted to Markdown when shown (`wiki_markdown`): templates dropped (the infobox is the fields), links kept as `[[…]]`. The DM's tools still get the raw text, as today. | No change to the DM's tool output; the web renders one format. |
| 13 | "Settings" for table options | The label becomes "Table options" ("Tafelopties"), and `…/play/settings` becomes `…/play/options`; the `play_settings` table keeps its name. | Spec anti-goal: no second "settings" in the UI or the API; the glossary already says "the table's options". |
| 14 | Stored names of Preferences | `delve.domain.settings.Settings`, `Storage.settings` and the `settings` table keep their names; the data dictionary records them. | A rename, not a redesign (spec); they aren't UI, API or glossary words. |
| 15 | The CLI | A thin client of the running Delve: it streams the picture to the same import route with the owner token, so the job runs, publishes and is reviewed in the app. Options `--cell`, `--distance`, `--units` as the API names them. | One conversion at a time is the server's rule; a second process running its own job would break it. |
| 16 | Where the proposal for the browser spec comes from | `fake_play_server.py` seeds it with `proposals.propose_fact` at start. | The browser check tests the organiser's side; the DM's side is `test_a_setting.py`'s scripted beat. |
